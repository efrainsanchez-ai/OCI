Chapter Purpose

This chapter defines the administrator access path for private resources in the PoC VCN baseline.
The consolidated runbook uses the pre-created (root)/Partner/LAD-01 compartment by default for the network baseline and any approved PoC administration resources. The assigned child compartment name can change for other deployments. Creating the Bastion VM itself is outside the scope of this runbook.

Preferred Model: OCI Bastion Service

Use OCI Bastion service where possible.

Advantages:

  • No persistent public jump-host compute instance.
  • No public IP needed on database nodes.
  • Time-bound sessions.
  • Identity-based access controls.
  • Auditable session creation and deletion.
  • Reduced patching and hardening burden compared with a traditional bastion host.

Session guardrail Short TTL with session creation and deletion audit events.
Private-only target No public IP or public listener path on Exadata nodes.

To protect exposure of the bastion public IP, allow Bastion access only from authorized administrator source IPs. Do not open TCP 22 to the public internet with 0.0.0.0/0; instead, register the authorized IPs or CIDR ranges in the bastion NSG.

Suggested SSH key protection tools:

OpenSSH FIDO-backed keys are not imported copies of regular SSH private key files. Use ed25519-sk or ecdsa-sk keys generated for the FIDO authenticator; the authenticator protects a non-exportable per-device private key. When resident keys are used, a FIDO2 authenticator can also store the key handle so the credential can be loaded on another trusted workstation after user verification.

OCI access and key storage guidance:

OCI capability Recommended role Guidance
OCI Bastion Primary SSH access control plane Use Bastion for restricted, time-bound access to private resources. Administrators provide the session public key and keep the private key client-side.
OCI Secret Management Service Controlled automation or break-glass storage Store SSH private keys only when there is an approved automation or emergency-access use case with strict IAM, audit, rotation, and retrieval controls. Do not use it as the default store for every administrator's personal private key.
OCI Vault / Key Management Encryption and signing key management Use Vault/KMS for OCI encryption, signing, and HSM-backed key management. Treat it as separate from a normal OpenSSH private-key wallet.
OCI Compute SSH key pairs Instance bootstrap credential OCI Compute uses the public key during instance creation. Oracle does not retain the generated private key, so the administrator must store it securely.
Platform Recommended tools Recommended use
macOS OpenSSH ssh-agent, Apple Keychain-backed passphrase storage, 1Password SSH Agent, OpenSSH FIDO-backed keys using FIDO2 security keys such as YubiKey Use passphrase-protected keys, prefer ed25519-sk or ecdsa-sk for privileged access where supported, store key passphrases in Keychain or an approved password manager, and avoid copying private keys between machines.
Linux OpenSSH ssh-agent, GNOME Keyring or KWallet, KeePassXC SSH Agent, 1Password SSH Agent, OpenSSH FIDO-backed keys using FIDO2 security keys such as YubiKey Keep private keys encrypted at rest, load keys only into a local agent, use separate named keys per administrator and environment, and prefer short-lived or hardware-backed credentials for production access.
Windows Windows OpenSSH Authentication Agent, Windows Hello-backed credential protection where available, 1Password SSH Agent, KeePassXC SSH Agent, PuTTY Pageant for PuTTY-based workflows, OpenSSH FIDO-backed keys using FIDO2 security keys such as YubiKey Use the built-in OpenSSH agent or an approved password-manager agent, protect private keys with passphrases, restrict filesystem permissions on key files, and avoid shared administrator keys.

For database listener testing after Exadata deployment, use SSH tunneling or a private application/tooling host. Do not expose SCAN or node listener ports publicly.

Approved Jump-Host Exception Model

Use a traditional jump host only when OCI Bastion service is not acceptable for the operating model.

If a Bastion VM is approved, place it in (root)/Partner/LAD-01 by default, or in the assigned Partner/<compartment> child compartment for the deployment, and attach it to the prepared admin subnet and NSG model. The workbook prepares the network controls only; it does not create or configure the VM.

4.2 Jump-host network rules

Direction Source / destination Protocol Port Purpose
Ingress 0.0.0.0/0 TCP 22 SSH from internet to the approved bastion/admin host
Egress Target NSGs TCP 22 SSH to nsg-exadata-client, nsg-applications, and nsg-dbtools-endpoint
Egress nsg-exadata-client TCP 1521, 6200 Admin SQL*Net validation and ONS/FAN over private subnet
Egress 0.0.0.0/0 through gw-internet route TCP All Approved outbound internet path for admin host operations

Shared NAT Gateway, Internet Gateway, and regional Oracle Services paths are controlled by the subnet route tables and the default security-list baseline. The backup subnet also attaches sl-backup for the Exadata backup access rules. The bastion/admin NSG keeps only the approved internet egress exception and target NSG access rules.

Validation

Confirm:

  • Bastion or jump-host access is reachable from approved sources only.
  • Private targets and managed public load balancer resources are reachable over TCP 22 only from the bastion/admin path.
  • Target Exadata subnets have no public SSH path.
  • Audit/logging captures session activity.
  • Security rules do not allow internet-to-Exadata SSH.
