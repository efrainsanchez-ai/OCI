Chapter Purpose

This chapter defines the administrator access path for private resources in the PoC VCN baseline.
The consolidated runbook uses the pre-created (root)/Partner/LAD-01 compartment by default for the network baseline and any approved PoC administration resources. The assigned child compartment name can change for other deployments. Creating the Bastion VM itself is outside the scope of this runbook.

Preferred Model: OCI Cloud Shell

Use OCI Cloud Shell as the preferred administrator workstation for this workbook. It provides an authenticated OCI CLI environment without requiring local OCI CLI installation or local API-key configuration. From Cloud Shell, connect through the approved Bastion VM to reach private resources.

Advantages:

  • Browser-based, OCI-authenticated administrator environment.
  • OCI CLI and common utilities are ready for workbook execution.
  • No local OCI API key, CLI profile, or workstation package installation is required.
  • The current Cloud Shell public IP can be restricted to a /32 SSH ingress rule on the Bastion VM NSG.
  • Database nodes and application targets remain private; Cloud Shell reaches them only through the approved bastion path.
  • Cloud Shell is ephemeral, reducing administrator workstation configuration drift.

Bastion Access Flow

1 ADM OCI Cloud Shell or Bastion VM Start in Cloud Shell from its public egress IP, or continue from an existing Bastion VM session.
Get public IP
2 BST Confirm source `/32` when using Cloud Shell Before a Cloud Shell connection, ensure its current public IP has TCP 22 ingress in nsg-bastion-admin.
SSH TCP 22
3 VCN Bastion VM Connect from Cloud Shell with the approved SSH user, or use the existing Bastion VM session as the controlled hop.
Private SSH
4 SSH Private target Reach an Exadata node or approved application host through target NSG rules.
Source gate Use the current source public IP as a `/32`; never allow 0.0.0.0/0.
Hop gate Only the Bastion VM has the approved public SSH endpoint.
Private-only target No public IP or public listener path on Exadata nodes.

The access flow can start from OCI Cloud Shell or from an existing Bastion VM session. When starting from Cloud Shell, before each SSH connection confirm that the current Cloud Shell public IP is registered as a /32 TCP 22 ingress rule in nsg-bastion-admin. The rule can be reused only while that public IP is unchanged; update it whenever Cloud Shell receives a different public egress IP. When already connected to the Bastion VM, continue to the private target through the approved target NSG rule. Do not open TCP 22 to the public internet with 0.0.0.0/0.

Suggested SSH key protection tools:

Create a new SSH key pair for Bastion VM access using a supported FIDO2 security key when hardware-backed administrator access is required. On a client with OpenSSH FIDO support, generate an ecdsa-sk key pair or, when the security key supports it, an ed25519-sk key pair. Install its public key in the approved administrator account's ~/.ssh/authorized_keys file on the Bastion VM. The key pair authorizes SSH access to the Bastion VM; the FIDO2 device protects the private credential used during authentication and that private material is not copied to the Bastion VM. When resident keys are used, the FIDO2 device can retain the key handle so the credential can be used from another trusted workstation after user verification.

Reference: Yubico — Securing SSH with FIDO2.

OCI access and key storage guidance:

For database listener testing after Exadata deployment, use SSH tunneling or a private application/tooling host. Do not expose SCAN or node listener ports publicly.

Approved Jump-Host Model

Use an approved Bastion VM when the operating model requires a persistent jump host. OCI Cloud Shell remains the preferred administrator workstation; the Bastion VM provides the controlled SSH hop to private targets.

If a Bastion VM is approved, place it in (root)/Partner/LAD-01 by default, or in the assigned Partner/<compartment> child compartment for the deployment, and attach it to subnet-admin and nsg-bastion-admin. Register the public IP address of the originating SSH host in nsg-bastion-admin as a TCP 22 ingress rule with a /32 CIDR. For example, when connecting from OCI Cloud Shell, add its current public IP as <cloud_shell_public_ip>/32. Do not use 0.0.0.0/0; update the rule when the originating host public IP changes.

4.2 Jump-host network rules

Direction Source / destination Protocol Port Purpose
Ingress <originating_host_public_ip>/32 TCP 22 SSH to the approved bastion/admin host; register this rule in nsg-bastion-admin
Egress Target NSGs TCP 22 SSH to nsg-exadata-client, nsg-applications, and nsg-dbtools-endpoint
Egress nsg-exadata-client TCP 1521, 6200 Admin SQL*Net validation and ONS/FAN over private subnet
Egress 0.0.0.0/0 through gw-internet route TCP All Approved outbound internet path for admin host operations

Shared NAT Gateway, Internet Gateway, and regional Oracle Services paths are controlled by the subnet route tables and the default security-list baseline. The backup subnet also attaches sl-backup for the Exadata backup access rules. nsg-bastion-admin is the control point for the source-specific SSH ingress rule, as well as approved internet egress and target-NSG access rules.

Validation

Confirm:

  • Bastion or jump-host access is reachable from approved sources only.
  • Private targets and managed public load balancer resources are reachable over TCP 22 only from the bastion/admin path.
  • Target Exadata subnets have no public SSH path.
  • Audit/logging captures session activity.
  • Security rules do not allow internet-to-Exadata SSH.
