Section purpose

This section stops and starts the compute-heavy parts of a non-production PoC environment when the environment does not need 24/7 operation. The stop path downscales VMCluster-01 enabled ECPUs to 0, stops the bastion VM with a graceful SOFTSTOP, and validates both resources after the change. The start path restores Exadata Exascale enabled ECPUs and starts the bastion VM when the service window reopens.
This action reduces runtime consumption, but it does not make the environment free. Storage, backup retention, stopped-instance storage, public IPs, logging, observability, private endpoints, and any other provisioned paid services can continue to accrue charges. Review OCI Cost Analysis, budgets, and the current Oracle Cloud price list before using this as a recurring shutdown procedure.

Independent administrator account model

This workbook is designed for an independent administrator account that can take over the environment without relying on a previous administrator's Cloud Shell home directory. BASH 01 creates the account-local ~/admin workspace, including cli.env, bin, lib, json, reports, and keys. The later cards rediscover the service OCIDs and names, restore only the required SSH keys from the private Object Storage bucket, and use the Bastion VM as the controlled path to the Exadata VM cluster.

Costs that can still be charged

Downscaling enabled ECPUs to 0 and stopping the bastion VM can reduce active compute charges, but the following resources can still appear in OCI usage and cost reports:

Resource or service Why charges can continue
Exadata Exascale storage Allocated database storage, VM file system storage, sparse or smart database storage, and any additional Exascale storage capacity remain provisioned.
Database backups Existing backups, automatic backup retention, Recovery Service protection, Object Storage backup copies, and retained backup metadata can continue to consume billable storage.
Bastion VM boot and block volumes Stopping the compute instance does not delete its boot volume or any attached block volumes. Storage remains allocated until deleted.
Reserved or public IPv4 addresses A reserved public IP or other billable public IPv4 resource can continue to charge even when the VM is stopped.
Object Storage Buckets and objects created by the workbook, including uploaded SSH key files or reports, remain stored until deleted.
Vault resources This workbook uses an Exascale storage vault for VM cluster storage and a DEFAULT Key Management vault for credential secrets. Software-protected Key Management vault keys and secrets are listed separately from Exascale storage vault capacity.
Database Management and observability Database Management, Operations Insights, Logging, VCN Flow Logs, Log Analytics, custom metrics, alarms, or other enabled management services can continue to charge according to service configuration and retained data.
Networking resources NAT Gateways, Load Balancers, Network Load Balancers, private endpoints, public IPs, and data transfer can continue to charge when provisioned or used.
Licenses and commitments Universal Credits, BYOL obligations, committed spend, support, marketplace subscriptions, and organization-specific contracts are outside this runbook and can still apply.

Use this runbook as a credit-saving control, not as a deletion procedure. To stop all charges, resources normally must be deleted and retained data must be removed according to your retention and compliance rules.

upsert_cli_env() {
  KEY="${1:-}"; VALUE="${2:-}"
  [ -n "$KEY" ] || { printf 'cli.env key is missing. Use upsert_cli_env KEY VALUE.\n' >&2; return 1; }
  case "$KEY" in *[!A-Z0-9_]* ) printf 'Invalid cli.env key: %s\n' "$KEY" >&2; return 1;; esac
  [ -n "$VALUE" ] && [ "$VALUE" != "null" ] || { printf '%s was not resolved. Review the command that produced this value before continuing.\n' "$KEY" >&2; return 1; }
  mkdir -p "$WORKBOOK_DIR"; touch "$CLI_ENV"; chmod 600 "$CLI_ENV"
  [ -s "$CLI_ENV" ] || printf 'set -a\nset +a\n' > "$CLI_ENV"
  grep -qx 'set -a' "$CLI_ENV" || { TMP_ENV="$(mktemp "$WORKBOOK_DIR/cli-env.XXXXXX")"; { printf 'set -a\n'; cat "$CLI_ENV"; } > "$TMP_ENV"; mv "$TMP_ENV" "$CLI_ENV"; }
  grep -qx 'set +a' "$CLI_ENV" || printf 'set +a\n' >> "$CLI_ENV"
  ESCAPED_VALUE="$(printf '%q' "$VALUE")"; TMP_ENV="$(mktemp "$WORKBOOK_DIR/cli-env.XXXXXX")"
  awk -v k="$KEY" -v v="$ESCAPED_VALUE" 'BEGIN{p=k"=";d=0} index($0,p)==1{next} $0=="set +a"&&!d{print k"="v;d=1} {print} END{if(!d)print k"="v}' "$CLI_ENV" > "$TMP_ENV"
  mv "$TMP_ENV" "$CLI_ENV"; chmod 600 "$CLI_ENV"
  export "$KEY=$VALUE"
  printf '%-18s | %s\n%-18s | %s\n%-18s | %s\n\n' \
    "VARIABLE" "VALUE" "------------------" "-----" "$KEY" "$VALUE"
}

profile_value() {
  awk -F= -v profile="$OCI_CONFIG_PROFILE" -v key="$1" '
    $0 == "[" profile "]" { in_profile=1; next }
    /^\[/ { in_profile=0 }
    in_profile && $1 ~ "^[[:space:]]*" key "[[:space:]]*$" {
      gsub(/[[:space:]]/, "", $2); print $2; exit
    }
  ' "$OCI_CONFIG_FILE"
}

wb16_card11() {

#!/bin/sh
. "$HOME/admin/bin/env.sh" --quiet || return 1

SOURCE_IP="${1:-}"
SOURCE_IP_MODE="${2:-provided}"
RULE_FILE="$JSON_DIR/nsg-bastion-ssh-source-rule.json"

  eval "value=\${$name:-}"

  --all \

    --nsg-id "$NSG_BASTION_OCID" \

printf '\n%s\n' "wb16_card12"

Node-count change follow-up

After an Exadata VM cluster node-count change, rerun these cards before using the new or changed nodes. This refreshes the independent administrator account's discovered values and avoids using a stale cluster host list.

  • BASH 01 - Prepare admin working files: rediscover the VCN, VM cluster, bastion, and related ~/admin/cli.env values.
  • BASH 02 - Review current service runtime state: confirm the updated VM cluster node count and lifecycle state.
  • BASH 13 - Create reusable cluster node SSH script: rediscover all node hostnames and rebuild ~/admin/bin/connect-cluster-node.sh.
  • BASH 14 - Mount File Storage on Exadata VM cluster nodes: rediscover the File Storage mount target and validate or mount FileSystem-01 on every current node.

Manual enabled-ECPU upscale or downscale follow-up

If an administrator changes the enabled ECPU count manually in the OCI Console or CLI, wait until the VM cluster returns to AVAILABLE, then follow this procedure:

  1. Run BASH 02 - Review current service runtime state to confirm the new enabled ECPU count and cluster state.
  2. Run BASH 03 - Save restore values to replace SERVICE_RESTORE_ENABLED_ECPU_COUNT with the newly approved enabled ECPU count before the next shutdown window.
  3. For a manual downscale to 0 that begins a shutdown window, run BASH 05 - Stop the bastion VM, then BASH 06 - Validate the shutdown state.
  4. For a manual upscale to a nonzero value, run BASH 10 - Validate started services. Run BASH 08 first only if the bastion VM is stopped and must be started.
  5. Do not rerun BASH 13 or BASH 14 for an enabled-ECPU-only change. Rerun them only when the VM cluster node count changes.
